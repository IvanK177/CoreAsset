# Спецификации CoreAsset

**Тема практики №149** — Сервис учёта рабочих мест с компьютерами: характеристики, ПО, лицензии, история неисправностей. Расширенная версия: ITAM & Service Desk.

---

## 1. Назначение системы

CoreAsset — веб-система для автоматизации учёта ИТ-активов предприятия, управления лицензиями ПО и координации сервисных служб (ИТ-поддержка и АХЧ). Система устраняет хаос в инвентаризации, предотвращает перерасход лицензий, обеспечивает оперативное решение инцидентов и даёт финансовую прозрачность по расходам на ПО.

**Целевая аудитория:** системные администраторы, ИТ-специалисты, специалисты АХЧ (завхозы), руководители ИТ-отделов, сотрудники организации и разработчики.

## 2. Функциональные требования

### Модуль A — Реестр сотрудников и Onboarding
| Приоритет | Требование |
|-----------|-----------|
| Высокий | Создание карточки сотрудника: ФИО, должность, email, кабинет, корпус размещения, телефон, Telegram |
| Высокий | Процесс Onboarding: при первом входе новый пользователь заполняет свои профильные данные и выбирает рабочий корпус |
| Высокий | Разграничение доступа на основе 5 ролей (Администратор, Сотрудник, ИТ-Специалист, Завхоз/АХЧ, Разработчик) |
| Средний | Механизм увольнения (Dismiss): перевод в статус «Неактивен» с автоматическим освобождением привязанных устройств |

### Модуль B — Реестр оборудования (Устройства)
| Приоритет | Требование |
|-----------|-----------|
| Высокий | Регистрация устройства: инвентарный номер, серийный номер, тип (ПК, Монитор, Клавиатура, Мышь, Принтер, Другое), кабинет, корпус |
| Высокий | Статусы жизненного цикла: Активен, В ремонте, Списан, На складе (Storage) |

| Средний | Управление софтом: просмотр установленного лицензионного ПО на карточке устройства с возможностью быстрой установки/удаления |

### Модуль C — Пулы лицензий ПО и Финансы
| Приоритет | Требование |
|-----------|-----------|
| Высокий | Справочник ПО и регистрация лицензий: тип (подписка / бессрочная), лимит мест, дата окончания подписки, цена за единицу |
| Высокий | Маскирование лицензионных ключей в UI с возможностью просмотра («глаз») и быстрого копирования |
| Средний | Контроль баланса: автоматическое изменение `used_seats` при привязке/удалении ПО; блокировка установки при исчерпании лимита |
| Средний | Аналитическая панель финансов: расчёт расходов по месяцам и годам, фильтрация по корпусам, вывод доли каждого ПО в общих затратах и экспорт отчёта в Excel (XLS) |
| Низкий | Визуальная индикация (красный цвет) для пулов с истекающей подпиской (< 30 дней) или исчерпанным лимитом мест |

### Модуль D — Журнал неисправностей (ИТ-инциденты)

|-----------|-----------|

## 3. Нефункциональные требования

### Безопасность
- **Аутентификация:** Supabase Auth (Email + Пароль), сессии через JWT в httpOnly cookies.
- **Ролевая модель (RBAC):** 
  - `admin` — полный доступ к управлению сотрудниками, ролями, устройствами, лицензиями, финансами и шаблонами.
  - `it_specialist` — просмотр инвентаря, управление шаблонами, управление инцидентами ИТ, чат с сотрудниками, SLA-календарь ИТ.
  - `facilities` — управление и выполнение заявок АХЧ на ремонт и оснащение, SLA-календарь АХЧ.
  - `employee` — просмотр своего профиля, Onboarding, просмотр закреплённых за ним устройств, создание инцидентов ИТ и заявок АХЧ, чат по своим тикетам, отправка обращений разработчикам.
  - `developer` — просмотр и закрытие обращений в поддержку.
- **Row Level Security (RLS):** Вся защита данных реализована на уровне СУБД PostgreSQL.
- **Целостность данных:** Каскадное удаление тикетов при удалении устройств (`ON DELETE CASCADE`); открепление сотрудников при удалении (`ON DELETE SET NULL`). Балансировка лицензий через PostgreSQL-триггеры. CHECK-ограничение `CHECK (used_seats <= total_seats)`.

### Производительность и оптимизация
- **Сжатие данных:**
  - Длинные описания инцидентов и заявок АХЧ сжимаются алгоритмом Gzip на клиенте/сервере перед записью в БД (префикс `gz:` в Base64).
  - Прикрепляемые фотоснимки сжимаются на стороне клиента до целевого размера перед загрузкой в Supabase Storage (`ticket-attachments`).
- **SLA-контроль времени:** Точный расчёт дедлайнов в соответствии с приоритетами по часовому поясу Москвы (Europe/Moscow).
  - Критический: 1 день.
  - Высокий: 2 дня.
  - Средний: 4 дня (ИТ) / 3-5 дней (АХЧ).
  - Низкий: 7 дней (ИТ) / 5-10 дней (АХЧ).
- **Поддержка PWA:** Service Worker (`sw.js`) для кэширования статических ресурсов и Toast-оповещения при выходе новых версий системы для мгновенного обновления без "залипаний" сессии.

## 4. Критерии приёмки

1. Запись об устройстве создаётся, редактируется и удаляется с обязательным подтверждением в модальном окне.
2. Привязка лицензии ПО к устройству увеличивает счётчик `used_seats` на 1; при превышении лимита транзакция блокируется базой данных.
3. Закрытые ИТ-инциденты и заявки АХЧ не удаляются из системы и сохраняются в архиве.
4. Доступ к API и страницам разграничен согласно ролевой модели (RLS-политики возвращают ошибку 403 при несанкционированном доступе).
5. Страница Финансов корректно рассчитывает ежемесячные расходы и экспортирует данные в XLS-файл.
6. PWA-уведомление предлагает обновиться при изменении Service Worker.
7. Проект задеплоен на Vercel и доступен по публичному адресу.
