# Технический долг — CoreAsset

В ходе анализа архитектуры, исходного кода и настроек безопасности проекта **CoreAsset** был сформирован перечень актуального технического долга, требующего внимания.

---

## 🟡 1. Проблемы архитектуры и поддерживаемости (Средний приоритет)

### 1.1. Сжатие текста в базе данных (GZIP `gz:<base64>`)
* **Описание:** Описания инцидентов (`description` в таблице `incidents` и запросах АХЧ) сжимаются с помощью GZIP на уровне API (`compressText`) и записываются в БД в формате `gz:Base64String`.
* **Последствия:**
  - Полностью ломается возможность полнотекстового поиска (Full-Text Search) средствами PostgreSQL по описаниям инцидентов.
  - Затрудняется прямая аналитика и написание SQL-запросов (в Supabase Studio данные отображаются в нечитаемом закодированном виде).
  - Усложняется фронтенд: для отображения текста везде приходится использовать специальный оберточный компонент `<DecompressedText />`.
* **Решение:** Отказаться от сжатия текста в БД. База данных PostgreSQL отлично справляется с хранением текстовых полей, а gzip-сжатие должно происходить на уровне сетевого протокола HTTP (Gzip/Brotli) средствами Next.js/Vercel.

### 1.2. Жестко закодированные пароли и UUID в Demo Sign-In
* **Описание:** Функция `demoSignIn` в [app/(auth)/login/actions.ts](file:///c:/Users/TopMob/Documents/Projects/Ivank/CoreAsset/app/(auth)/login/actions.ts) использует фиксированный пароль `"demo123password"` и статические UUID сотрудников (`a0000000-0000-...`, `e0000001-0000-...`).
* **Текущее состояние:** Демо-панель на UI была успешно скрыта от пользователей за секретным триггером (3 клика по логотипу), но сами жестко закодированные учетные данные остаются в коде экшена.
* **Последствия:** Если проект будет развернут на публичном хостинге без отключения демо-входа, злоумышленники смогут войти под учетными записями администраторов, используя статические UUID и фиксированный пароль, отправив прямой POST-запрос.
* **Решение:** Вынести демо-режим под флаг переменной окружения (например, `ENABLE_DEMO_LOGIN=true`), а пароли и UUID генерировать динамически или хранить в закрытом `.env.local`.

## 🟢 2. Качество кода и автоматизация (Низкий приоритет)

### 2.1. Ошибки линтинга (ESLint) и использование `any`
* **Описание:** Команда `npm run lint` завершается с ошибками (10 ошибок, 5 предупреждений):
  - В [ThemeToggle.tsx](file:///c:/Users/TopMob/Documents/Projects/Ivank/CoreAsset/components/shared/ThemeToggle.tsx) вызов `setMounted(true)` вызывается синхронно в теле `useEffect`, что вызывает каскадные рендеры.
  - Во многих файлах (например, [auth.ts](file:///c:/Users/TopMob/Documents/Projects/Ivank/CoreAsset/lib/actions/auth.ts), [client.ts](file:///c:/Users/TopMob/Documents/Projects/Ivank/CoreAsset/lib/supabase/client.ts)) используется тип `any` вместо строгого типизирования (`@typescript-eslint/no-explicit-any`).
  - Есть неиспользуемые импорты в серверных экшенах (например, `createClient` и `cookies` в [support.ts](file:///c:/Users/TopMob/Documents/Projects/Ivank/CoreAsset/lib/actions/support.ts)).
* **Последствия:** Риск снижения производительности на клиенте, ухудшение типизации (потеря преимуществ TypeScript) и накопление неиспользуемого кода.
* **Решение:** Исправить логику `ThemeToggle` для предотвращения каскадных рендеров, заменить типы `any` на строгие интерфейсы и удалить лишние импорты.

### 2.2. Полное отсутствие автоматических тестов
* **Описание:** В проекте нет ни одного unit-теста, интеграционного или E2E-теста.
* **Последствия:** Риск регрессии при изменении схемы БД, политик RLS или Server Actions. При обновлении зависимостей баги могут быть обнаружены только при ручном тестировании.
* **Решение:** Установить `vitest` для юнит-тестирования Server Actions/утилит и настроить базовые тесты для проверки RLS-политик Supabase.

### 2.3. Отсутствие валидации переменных окружения на старте
* **Описание:** Переменные окружения (`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и др.) используются в коде через оператор `!`, без предварительной валидации.
* **Последствия:** При неправильной конфигурации или пропущенной переменной приложение падает с трудночитаемыми runtime-ошибками в случайных местах.
* **Решение:** Создать скрипт валидации конфигурации (например, с использованием Zod) при запуске приложения, чтобы сразу сообщать о пропущенных переменных.

### 2.4. Недоработки PWA (Офлайн-режим)
* **Описание:** В архитектурных концептах упоминается идея создания офлайн-очереди изменений (Offline Queue) для тикетов, чтобы инженеры могли работать без стабильного интернета. На данный момент Service Worker умеет кэшировать только статику, но логика синхронизации изменений (`IndexedDB` / `localforage`) не реализована.
* **Решение:** Интегрировать `localforage` для накопления оффлайн-действий и отправки их на сервер при восстановлении сети.
