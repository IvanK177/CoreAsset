# Технический долг — CoreAsset

В ходе анализа архитектуры, исходного кода и настроек безопасности проекта **CoreAsset** были выявлены следующие технические долги и уязвимости. Они разделены по категориям критичности.

---

## 🔴 Критические проблемы безопасности (✅ Исправлено)

**Проблема 1**: Отсутствовал файл защиты роутов — любой неавторизованный пользователь мог напрямую зайти на `/dashboard`, `/it-portal`, `/dev-portal` и т.д. В лейаутах при отсутствии сессии происходил авто-фолбек на первого админа из БД → утечка персональных данных.

**Решение**: Создан/активирован файл `proxy.ts` (современная замена `middleware.ts` в Next.js 16) в корне проекта с проверкой сессии Supabase Auth через `getUser()`. Удалены все небезопасные авто-фолбеки из лейаутов и страниц порталов.

---

**Проблема 2**: Server Actions использовали `service_role` без проверки прав — обходили RLS.

**Решение**: Добавлена утилита `requireAuth()` в `lib/actions/auth.ts`. Все Server Actions теперь проверяют сессию и роль перед операцией.

**Результат**: Доступ к роутам и операциям ограничен по ролям, RLS-политики защищены.

---

## 🟡 Проблемы архитектуры и поддерживаемости (Средний приоритет)

### 3. Сжатие текста в базе данных (GZIP `gz:<base64>`)
* **Описание:** Описания инцидентов (`description` в `incidents`) и запросов АХЧ сжимаются с помощью GZIP на уровне API (`compressText`) и записываются в БД в формате `gz:Base64String`.
* **Последствия:**
  - Полностью ломается возможность полнотекстового поиска (Full-Text Search) средствами PostgreSQL по описаниям инцидентов.
  - Затрудняется прямая аналитика и написание SQL-запросов (в Supabase Studio или внешних клиентах данные отображаются в нечитаемом зашифрованном виде).
  - Усложняется фронтенд: для отображения текста везде приходится использовать специальный оберточный компонент `<DecompressedText />`.
* **Решение:** Отказаться от сжатия текста в БД. База данных PostgreSQL отлично справляется с хранением текстовых полей (`text`/`varchar`), а gzip-сжатие должно происходить на уровне сетевого протокола HTTP (Gzip/Brotli в Next.js/Vercel).

### 4. Жестко закодированные пароли и UUID в Demo Sign-In
* **Описание:** Функция `demoSignIn` в `app/(auth)/login/actions.ts` использует фиксированный пароль `"demo123password"` и статические UUID сотрудников (`a0000000-0000-...`, `e0000001-0000-...`).
* **Последствия:** Если проект будет развернут на публичном хостинге/production без отключения демо-входа, злоумышленники смогут легко войти под учетными записями администраторов и разработчиков, используя эти фиксированные идентификаторы.
* **Решение:** Вынести демо-режим под флаг переменной окружения (например, `ENABLE_DEMO_LOGIN=true`), а пароли и UUID генерировать динамически или хранить в зашифрованном виде в `.env.local`.

## 🟢 Качество кода и автоматизация (Низкий приоритет)

### 5. Полное отсутствие автоматических тестов
* **Описание:** В проекте нет ни одного unit-теста, интеграционного или E2E-теста. В `package.json` отсутствуют тестовые зависимости (Jest, Vitest, Playwright, Cypress).
* **Последствия:** Риск регрессии при изменении схемы БД, политик RLS или Server Actions. При обновлении зависимостей или логики Next.js баги могут быть обнаружены только при ручном тестировании.
* **Решение:** Установить `vitest` для юнит-тестирования Server Actions/утилит и настроить базовые тесты для проверки RLS-политик Supabase.

### 6. Отсутствие валидации переменных окружения на старте
* **Описание:** Переменные окружения (`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и др.) используются в коде через оператор `!`, без предварительной валидации.
* **Последствия:** При неправильной конфигурации или пропущенной переменной приложение падает с трудночитаемыми runtime-ошибками в случайных местах.
* **Решение:** Создать скрипт валидации конфигурации (например, с использованием Zod) при запуске приложения, чтобы сразу сообщать о пропущенных переменных.

### 7. Недоработки PWA (Офлайн-режим)
* **Описание:** В `docs/ai_architecture_insights.md` упоминается идея создания офлайн-очереди изменений (Offline Queue) для тикетов, чтобы инженеры могли работать без стабильного интернета. На данный момент Service Worker умеет кэшировать только статику, но логика синхронизации изменений (`IndexedDB` / `localforage`) не реализована.
* **Решение:** Интегрировать `localforage` для накопления оффлайн-действий и отправки их на сервер при восстановлении сети.
