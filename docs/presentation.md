Основной упор сделан на бизнес-ценность, архитектурные решения и сложные технические механизмы, которые выделяют проект на фоне типовых CRUD-приложений.

### Слайд 2: Проблематика бизнеса
* **Заголовок:** С какими проблемами сталкивается бизнес?
* **Визуальное оформление:** Инфографика или иконки, иллюстрирующие хаос: бумажные журналы, знак вопроса над лицензиями, часы (потеря времени).
* **Текст на слайде:**
  - **Теневое ИТ и потеря техники:** Отсутствие четкой связи между сотрудником и выданным ему оборудованием (особенно при увольнении).
  - **Перерасход бюджета на ПО:** Штрафы за нелицензионный софт или, наоборот, покупка лишних подписок из-за отсутствия контроля занятых слотов.
  - **Разрозненность процессов:** ИТ-отдел и завхозы используют разные каналы (почта, мессенджеры, бумажные заявки) — как итог, теряется история ремонтов и срываются сроки.
* **Речь докладчика:**  
  «В ходе анализа предметной области мы выделили три ключевые проблемы. Во-первых, при увольнении сотрудников компания часто теряет технику из-за ручного учета. Во-вторых, из-за отсутствия контроля пула лицензий компании либо переплачивают за неиспользуемый софт, либо получают штрафы за превышение лимитов. В-третьих, заявки в ИТ и АХЧ поступают хаотично через мессенджеры, что делает невозможным контроль сроков выполнения (SLA). CoreAsset решает все эти проблемы.»

### Слайд 3: Цели и Архитектура решения
* **Заголовок:** Архитектура и стек технологий
* **Визуальное оформление:** Наглядная схема архитектуры: Client UI (Next.js 16) ⚡ Server Actions ⚡ Supabase (PostgreSQL + Auth + Storage).
* **Текст на слайде:**
  - **Фронтенд & Бэкенд:** Next.js 16 (App Router, Turbopack) — единый монорепозиторий, интеграция через Server Actions (без REST API).
  - **База данных:** Supabase (PostgreSQL) — реляционная структура, триггеры, индексы.
  - **UI/UX:** Tailwind CSS v4, shadcn/ui, полная поддержка темной и светлой тем.
* **Речь докладчика:**  
  «Для реализации мы выбрали современный стек. Ядро системы построено на Next.js 16 с использованием App Router. Особенность нашей архитектуры — отказ от классического REST API в пользу Server Actions, что обеспечивает строгую типизацию от фронтенда до базы данных. В качестве базы данных используется мощная реляционная СУБД PostgreSQL на базе облака Supabase, которая также предоставляет нам хранилище файлов (Storage) и систему авторизации.»

### Слайд 4: Инновационная безопасность (RLS)
* **Заголовок:** Ролевая модель и Row Level Security
* **Визуальное оформление:** Иллюстрация "щита" на уровне базы данных. Скриншот страницы входа (`/login`) с панелью быстрого демо-входа (5 кнопок).
* **Текст на слайде:**
  - **5 ролей:** Администратор, ИТ, АХЧ, Сотрудник, Разработчик.
  - **Row Level Security (RLS):** Безопасность гарантирована на уровне СУБД, а не приложения.
  - **Security Definer:** Изолированные функции PostgreSQL для проверки ролей.
* **Речь докладчика:**  
  «Безопасность данных — критический аспект корпоративных систем. В CoreAsset реализовано 5 ролей. Главная техническая особенность: разграничение прав реализовано не в коде приложения, а прямо на уровне базы данных с помощью механизма Row Level Security (RLS) в PostgreSQL. Даже если злоумышленник найдет уязвимость в API, СУБД физически не отдаст ему чужие данные. Для удобства комиссии на странице авторизации мы добавили панель демо-входа — вы можете переключаться между ролями в один клик.»

### Слайд 5: Автоматизация управления персоналом
* **Заголовок:** Жизненный цикл сотрудника: Onboarding и Увольнение
* **Визуальное оформление:** Два скриншота: экран приветственного онбординга (`/onboarding`) и таблица реестра сотрудников с бейджами статусов.
* **Текст на слайде:**
  - **Авто-онбординг:** Маршрутизация новых пользователей на заполнение профиля (корпус, кабинет, должность).
  - **Профиль:** Вся история техники и тикетов сотрудника в одной карточке.
  - **Бизнес-логика увольнения:** При деактивации сотрудника вся техника автоматически открепляется и переходит на статус "Склад".
* **Речь докладчика:**  
  «Система автоматизирует работу с персоналом. При первом входе новый сотрудник перенаправляется на экран онбординга для выбора своего рабочего места. Самая важная бизнес-логика кроется в механизме увольнения: как только администратор деактивирует учетную запись сотрудника, система автоматически отвязывает от него всё числящееся оборудование и лицензии, возвращая их на виртуальный склад. Это полностью исключает риск потери активов.»

### Слайд 7: Управление лицензиями ПО (Software Asset Management)
* **Заголовок:** Строгий контроль лицензий и защита ключей
* **Визуальное оформление:** Скриншот таблицы лицензий (`/licenses`). Акцент на замаскированные ключи (••••) и индикатор исчерпания лимитов (красный/зеленый прогресс-бар).
* **Текст на слайде:**
  - **Типы лицензий:** Подписки (SaaS) и бессрочные ключи (Perpetual).
  - **Защита данных:** Ключи скрыты в интерфейсе, доступ только по кнопке.
  - **СУБД-триггеры контроля:** База данных аппаратно блокирует привязку ПО, если лимит рабочих мест (seats) исчерпан.
* **Речь докладчика:**  
  «Раздел лицензий — гордость нашего проекта. Ключи активации по умолчанию замаскированы для защиты от посторонних глаз в опенспейсе. Чтобы предотвратить штрафы от вендоров за перерасход лицензий, мы написали специальные триггеры в PostgreSQL. Если компания купила 50 лицензий Photoshop, система на уровне базы данных выдаст ошибку при попытке установить его на 51-й компьютер, обеспечивая 100% комплаенс.»

### Слайд 10: Service Desk АХЧ и контроль SLA
* **Заголовок:** Портал АХЧ: Заявки на ремонт и SLA-трекинг
* **Визуальное оформление:** Скриншот портала АХЧ с выделенными бейджами дедлайнов (SLA) и фотографиями "До / После".
* **Текст на слайде:**
  - **Изолированный портал:** Завхозы видят только свои задачи (ремонт, мебель, клининг).
  - **Контроль SLA (Service Level Agreement):** Автоматический расчет крайнего срока (1-10 дней) в зависимости от приоритета задачи.
  - **Фотоотчеты "До / После":** Строгий контроль качества выполнения работ завхозами.
* **Речь докладчика:**  
  «Кроме ИТ, в системе есть отдельный портал для административно-хозяйственной части (АХЧ). Заявки на ремонт мебели или замену ламп не смешиваются с ИТ-инцидентами. Здесь мы внедрили систему контроля SLA — в зависимости от приоритета заявки система автоматически рассчитывает дедлайн. А чтобы избежать отписок, закрыть заявку АХЧ можно только прикрепив фотографию результата работы.»

### Слайд 11: Технические оптимизации (Сжатие и PWA)
* **Заголовок:** Оптимизация производительности и PWA
* **Визуальное оформление:** Техническая схема: Canvas-сжатие картинок -> Gzip-алгоритм текста (`gz:`) -> Supabase. Плашка PWA "Установить на экран".
* **Текст на слайде:**
  - **Gzip-компрессия:** Алгоритмическое сжатие длинных описаний в формат base64 для экономии места в СУБД.
  - **Canvas-сжатие фото:** Изображения сжимаются на стороне клиента *до* отправки на сервер (экономия трафика и хранилища).
  - **Progressive Web App (PWA):** Кэширование статики через Service Worker, возможность установки как приложения на ПК и смартфон.
* **Речь докладчика:**  
  «Для обеспечения быстрой работы мы реализовали ряд нестандартных оптимизаций. Фотографии отчетов сжимаются через HTML5 Canvas прямо в браузере ДО отправки, что экономит дорогое облачное хранилище. Длинные описания сжимаются алгоритмом Gzip. Кроме того, приложение поддерживает технологию PWA — оно устанавливается на компьютер или телефон как нативная программа и кэширует ресурсы для быстрой загрузки даже при плохом интернете.»
